# ShapeDesignGUI Report Notes

## Project overview

ShapeDesignGUI is an IDE for a small graphics language used to describe diagrams with
lines, rectangles, circles, text, scoped drawing colours, and filled shapes. The main use
case is drawing simple chart diagrams such as bar charts and pie charts.

The application is split into a Java Swing GUI and a Scala drawing backend. The Java side
is responsible for the editor, buttons, grid viewer, error panel, and converting backend
results into Swing drawing data. The Scala side is responsible for parsing the graphics
language, storing drawing state such as the active bounding box and current colour, and
producing the points/text that should be drawn.

This split is important because the coursework requires that the Java GUI does not own the
drawing engine state. In this project, the Java code passes the editor contents directly
to the Scala interpreter through `DrawingEngine` methods. It does not split or rewrite the
graphics program before interpretation.

## User interface

The main window has a graphics viewer on the left and a language editor on the right. The
viewer displays a grid and draws the interpreted output from the editor. The right side
contains:

- a `Draw` button,
- buttons for loading the pie chart and bar chart examples,
- a text editor containing the graphics language program,
- an error/status area.

When the user presses `Draw`, the Java GUI reads the editor text and passes it to the Scala
backend. If parsing or interpretation succeeds, the GUI updates the bounding box, points,
and text labels in the viewer. If parsing or interpretation fails, the GUI shows the error
message in the error panel instead of crashing.

Two reproducible example programs are included:

- `docs/examples/pie-chart.shape`
- `docs/examples/bar-chart.shape`

The GUI also contains bundled fallback versions of these examples, so the demo can still
load an example if the external file cannot be read.

## Graphics language

The implemented language supports the commands required by the coursework:

- `(BOUNDING-BOX (x1 y1) (x2 y2))`
- `(LINE (x1 y1) (x2 y2))`
- `(RECTANGLE (x1 y1) (x2 y2))`
- `(CIRCLE (x y) r)`
- `(TEXT-AT (x y) "text")`
- `(DRAW colour g1 g2 ...)`
- `(FILL colour g)`

The parser enforces two top-level validity rules:

- the first command must be `BOUNDING-BOX`,
- there must be exactly one top-level `BOUNDING-BOX`.

The drawing engine interprets commands in program order. The active bounding box is stored
in Scala state and is used to clip points and text. Colour is also stored in Scala state.
Outside a `DRAW` or `FILL` command the default colour is black. Inside `DRAW`, all nested
commands are interpreted with the specified colour. Inside `FILL`, the filled object is
interpreted with the specified fill colour. After a scoped colour command finishes, sibling
commands continue with the previous colour.

## Drawing algorithms

Lines are generated in Scala by `Draw.drawLineSc`, which implements Bresenham-style line
stepping. Rectangles are drawn as four lines. Circles are generated by `Draw.drawCircleSc`,
which follows the midpoint circle algorithm and emits symmetric points around the centre.

The drawing engine converts generated geometry into drawable output:

- points become `DrawablePoint(x, y, colour)`,
- text commands become `DrawableText(x, y, text, colour)`.

When a bounding box is active, generated points are filtered through `insideBox`. Text is
also emitted only when its coordinate is inside the active bounding box.

## Testing strategy

The project uses runtime tests for both the Scala backend behavior and Java GUI component
behavior.

The backend tests in `src/test/java/types/DrawingEngineTest.java` check:

- programs are rejected when `BOUNDING-BOX` is not first,
- programs are rejected when multiple top-level bounding boxes are present,
- generated points are clipped to the bounding box,
- `DRAW` colour scope does not leak to following sibling commands,
- the required bounding box can be retrieved from a valid program.

The Java component tests in `src/test/java/parts/GridBackgroundPanelTest.java` check the
coordinate conversion behavior used by the grid panel, especially the conversion from
graphics coordinates to screen Y coordinates with and without a bounding box.

These tests give executable evidence for parser validation, clipping behavior, colour
scope, and Java-side coordinate handling.

## Logika verification

The project also includes Sireum Logika proof worksheets under `src/logika/`. These are
proof-oriented models of selected correctness properties from the production Scala code.
They are intentionally small and separate from `src/main/scala` so that Maven does not try
to compile Logika-specific worksheet code.

The Logika artifacts are:

- `src/logika/ParserTopLevelProof.sc`
- `src/logika/ClippingSafetyProof.sc`
- `src/logika/ColorScopeProof.sc`
- `src/logika/GeometryInvariantsProof.sc`

The parser proof models the top-level validity checks: a normally accepted program must
have a non-empty command list, the first command must represent a bounding box, and there
must be exactly one bounding box.

The clipping proof models the safety condition behind `insideBox` and clipping: if a point
or text position is emitted under an active bounding box, its coordinates satisfy the
bounding-box bounds.

The colour-scope proof models the intended semantics of `DRAW` and `FILL`: the inner
command uses the scoped colour, while sibling commands keep the previous outer colour.

The geometry proof models local invariants of the drawing algorithms. For Bresenham-style
line stepping, it captures that each enabled axis changes by at most one signed step. For
midpoint-circle drawing, it captures that each generated point belongs to the eight-way
symmetry set around the circle centre.

The important limitation is that these are not a full formal verification of the entire
Swing application or the full production Scala parser. They are Logika-checked models of
the core properties, mapped back to the implementation and supported by runtime tests.
This is the most accurate claim for the report:

> Selected core properties were modeled and checked with Sireum Logika: parser top-level
> validity, clipping safety, colour scoping, and geometry helper invariants. The production
> Scala and Java implementation is also covered by runtime tests. The Logika proofs are
> proof-oriented models mapped to the implementation, not a full formal verification of
> the entire application.

## Known limitation

The coursework mentions that the currently drawn object should be highlighted while the
graphics is drawn. This feature is not implemented in this delivery and should be stated
explicitly as a known limitation in the report and demo.

## How to run

With Java and Maven installed:

```bash
mvn test
mvn exec:java -Dexec.mainClass=Main
```

With Sireum installed, the Logika worksheets can be checked with:

```bash
sireum logika src/logika/ParserTopLevelProof.sc
sireum logika src/logika/ClippingSafetyProof.sc
sireum logika src/logika/ColorScopeProof.sc
sireum logika src/logika/GeometryInvariantsProof.sc
```
